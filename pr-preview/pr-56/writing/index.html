論文の書き方の手引き

この手引きは、論文やレポートを書くときに気を付けてほしいことをまとめたものです。 週報、各種レポート、卒業論文、修士論文、学会の原稿のどれにも当てはまります。 以下では、これらをまとめて「論文」と呼びます。

ここに挙げたのは、これまでの添削で特に多く指摘してきたことです。 書き始める前に一度読み、PR(プルリクエスト)を送る前にもう一度読み返してください。 添削のコメントで、この手引きの項目を示すことがあります。

前の章ほど論文全体に関わる話で、後の章ほど細かい話です。 書き始めるときは前の章を、書き上げて読み返すときは後の章を中心に確かめてください。

各項目は、次の形で書いています。

  • なぜ: それを直さないと、読者に何が起こるか
  • 悪い例と良い例: 直す前と直した後の文(どれも架空のもの)
  • 確かめる問い: 自分の原稿を読み返すときに、自分に問いかけてほしいこと

例文は論文の文体(である体)で書いています。

目次

  1. 何を伝える論文かをはっきりさせる
  2. 読者が付いて来られるようにする
  3. したことを省かずに書く
  4. 話の流れを整える
  5. 文を整える
  6. 語を選ぶ
  7. 提出前のチェックリスト

1. 何を伝える論文かをはっきりさせる

1.1 目的と手段を分ける

なぜ: 「〜を開発する」「〜を用いて〜する」は手段です。 手段だけを書くと、それができると誰の何が良くなるのかが読者に伝わらず、研究が成功したかどうかも判断できません。 問題を「〜がない」のように、手段がない形で書くのも同じです。 先に何を良くしたいのかを書き、その後で、そのために何を使うのかを書いてください。

悪い例

本研究の目的は、位置情報を用いた蔵書検索アプリを開発することである。

現在の図書室には、蔵書検索アプリがないことが問題である。

良い例

本研究の目的は、利用者が探している本を書架で見つけるまでの時間を短くすることである。 そのために、利用者の位置を用いて本までの道順を示す。

現在の図書室では、利用者が探している本を見つけるまでに平均10分かかっていることが問題である。

確かめる問い: それは手段ではありませんか。 その道具を使うことになったのは、そもそも何がしたかったからですか。 それができると、誰の何が良くなりますか。

1.2 研究の位置づけを示す

なぜ: 元になった研究や、似たことをしている研究に触れないと、読者はこの研究の何が新しいのか判断できません。 研究室の先輩が作ったシステムを引き継いだ場合も、その論文を引用してください。 同じ問題に対して世の中でどんな方法が使われていて、この研究がその中のどこにあるのかを書きます。 探しても見つからなかったときは、どこを調べたのかを書いてください。

悪い例

当研究室では、貸出管理システムを開発してきた。 本研究では、このシステムに予約機能を加える。

良い例

当研究室では、貸出管理システム[5][6]を開発してきた。 市販の図書館システム[7]は大規模な図書館を対象とする。 これに対し、当研究室のシステムは研究室の本棚のような小規模な蔵書を対象とする。 本研究では、このシステムに予約機能を加える。

確かめる問い: このシステムの元になった論文はどれですか。 似たことをしている研究を調べましたか。 自分の研究は、ほかの方法と比べてどこが違いますか。

1.3 選んだ理由を書く

なぜ: 技術、方式、パラメータ、閾値などを選んだ理由がないと、読者には「たまたまそうした」のか「考えてそうした」のかが分かりません。 試行錯誤の過程までは要りません。 最終的に選んだ理由を書いてください。

悪い例

位置情報の取得間隔は10秒とした。

良い例

位置情報の取得間隔は10秒とした。 停留所への接近を判定するには、停留所の間で少なくとも3回位置を取得し、進む向きを求める必要がある。 停留所の間の最短の走行時間は約30秒なので、10秒間隔なら3回取得できる。

確かめる問い: どうしてこの方式や値を選んだのですか。 ほかの選択肢では駄目だったのですか。

1.4 主張の強さを根拠に合わせる

なぜ: 根拠より強く言い切ると、読者は信用しなくなります。 逆に、根拠があって言い切れることを「考えられる」でぼかすと、誰の意見なのか分からなくなります。 言い切るときは、その根拠も書いてください。

悪い例

貸出手続きの遅れの原因は入力画面にあると考えられる。 実験によりこの方式の優位性を証明した。 大学の授業では、出席確認に紙の名簿が使われている。

良い例

貸出手続きの所要時間を計測したところ、7割を入力画面での操作が占めていた。 したがって、貸出手続きの遅れの主な原因は入力画面にある。 実験の結果、この方式は比較した2方式より処理時間が短かった。 本学の授業担当者への調査[4]では、回答者の6割が出席確認に紙の名簿を使っていた。

確かめる問い: この語を使えるだけの根拠がありますか。 それは、どこでも同じですか。 「考えられる」は、言い切れませんか。

1.5 事実と意見を分ける

なぜ: 結果から言えることと、書き手がそこから考えたことが混ざると、読者はどこまでが確かな話なのか分かりません。 結果を述べる段落には測った事実を書き、解釈は「〜と考える」と分かる形で書いてください。 「わかった」「示している」と書くときは、その結果が本当にそこまで裏付けているかを確かめます。 「〜も」「〜しか」のような評価を含む語や、「筆者は」のような書き手の視点も、結果の記述には入れません。

悪い例

アンケートの結果から、本機能が学習意欲を高めることがわかった。 導入後の貸出冊数は、前月の1.2倍にもなった。

良い例

アンケートでは、回答者の8割が「使いやすい」を選んだ。 導入後の貸出冊数は、前月の1.2倍であった。 これらの結果から、本機能は図書室の利用を増やす可能性があると考える。

確かめる問い: これは結果から言える事実ですか。 それとも自分の意見ですか。 前で「考えられる」と書いたことを、後で事実として扱っていませんか。

1.6 題名、概要、序論、まとめを本文とそろえる

なぜ: 多くの読者は、題名、概要、序論、まとめを読んで、何をした研究なのかをつかみます。 これらと本文が食い違うと、読者は研究の中身を取り違えます。 書き上げたら、題名の語が目的と概要に出てくるか、目的の書き方が序論とまとめで同じか、まとめに本文にない話が入っていないかを確かめてください。 見出しや「本章では〜を述べる」という予告も、本文の内容と合わせます。 概要には、背景だけでなく、したことと結果まで書いてください。

悪い例

(題名)蔵書検索の高速化 (まとめ)本研究では、操作画面を見やすくした。

良い例

(題名)蔵書検索の高速化 (まとめ)本研究では、蔵書検索を高速化した。 評価では、本を見つけるまでの時間が平均10分から3分に短くなった。 今後の課題は、書架の配置が変わったときに地図を更新する方法である。

確かめる問い: 概要だけを読んだ人に、何をしたのか伝わりますか。 まとめに書いた話は、本文のどこにありますか。 見出しと、その下の本文は合っていますか。

2. 読者が付いて来られるようにする

2.1 内容を章や節の役割に合う場所に置く

なぜ: 論文の章や節には、背景、目的、設計、実装、評価、まとめのような役割があります。 役割と違う内容が混ざると、読者は今どの段階の話を読んでいるのか分からなくなります。 背景の節に自分の取り組みを書いたり、問題点の節に解決策を混ぜたりしないでください。 開発の経緯を時系列に語るのではなく、最終的にできたものを説明します。 章をつなぐために、次の章の内容に一言触れるのは構いません。

悪い例

(研究背景の節で)傘を持たずに出かけて、雨に降られる人は多い。 そこで本研究では、通知機能を持つアプリを開発した。

良い例

(研究背景の節で)傘を持たずに出かけて、雨に降られる人は多い。 (研究目的の節で)本研究の目的は、傘の持ち忘れを減らすことである。

確かめる問い: この内容は、この章に書く話ですか。 背景と、本研究でしたことを分けて書いていますか。

2.2 何の話かを先に示す

なぜ: 全体が何なのかを知らないうちに部品や設定値の説明が始まると、読者は何のための話か分からずに読むことになります。 前に出てこなかった話題が急に始まるのも同じで、読者はなぜその話になったのか分からず、置いていかれます。 章、節、段落の初めに、それが全体として何なのか、これから何を説明するのかを書いてください。 新しい話を始めるときは、その話が必要になる理由を先に書きます。

悪い例

本アプリは画面部、通知部、記録部の3つで構成される。 画面部は天気データを10分ごとに取得する。

本研究の目的は蔵書検索の高速化である。 そこで、書架の配置図を作成した。

良い例

本アプリは、外出前に傘が必要かどうかを利用者に知らせる。 本章では、まず全体の流れを述べ、その後で画面部、通知部、記録部を順に説明する。

本研究の目的は蔵書検索の高速化である。 検索の所要時間は、本の探索範囲に左右される。 そこで、探索範囲を絞るため、書架の配置図を作成した。

確かめる問い: それを知らない人に一言で説明するとしたら、何と言いますか。 この話は前に出てきましたか。 なぜここでこの話が始まるのか、読者に分かりますか。

2.3 読者の前提知識に合わせて説明する

なぜ: 自分や研究室では当たり前のことでも、初めて読む人には分かりません。 読者は、同じ分野の1学年下の学生、または研究を始める前の自分だと考えてください。

悪い例

位置の補正には XYZ を用いた。 貸出台帳を移行した。

良い例

位置の補正には XYZ(Extended Yard Zoning)を用いた。 XYZ は地図を格子に区切って座標を補正する手法である[1]。 貸出台帳は、図書室が利用者ごとの貸出履歴を記録している表である。 本研究ではこれを移行した。

確かめる問い: この略語は何の略ですか。 初めて読む人は、これで全体像を想像できますか。

2.4 説明する前に使わない

なぜ: 自分で作った語やシステムの中でだけ意味を持つ語(画面名、機能名、データ名)を説明なしに使うと、読者はそこで止まってしまいます。 説明は、その語を最初に使う前に書いてください。 後で説明するなら、どこで説明するかを書きます。

悪い例

通知は配信枠の残量に応じて送信する。 (以降の節で)配信枠とは、1日に送信できる通知の上限である。

良い例

1日に送信できる通知の上限を配信枠と呼ぶ。 通知は配信枠の残量に応じて送信する。

確かめる問い: この語は、ここまでに出てきましたか。 事情を知らない人にも伝わりますか。

3. したことを省かずに書く

3.1 機能は仕組みまで書く

なぜ: 「何ができるか」だけでは、どう作ったのかが読者に伝わりません。 データをどこから取り、どこへ保存するのか、操作の後に何が起こるのか、条件に合わないときはどうなるのかを書いてください。

悪い例

返却ボタンを押すと、返却処理を行う。

良い例

返却ボタンを押すと、貸出表の該当行に返却日時を記録し、一覧画面に戻る。 貸出中でない本を選んだ場合は警告を表示する。

確かめる問い: この機能をどうやって実現しましたか。 この値の出どころと保存先はどこですか。 ボタンを押したら何が起こりますか。

3.2 使った技術の役割と、実験の条件を書く

なぜ: 技術の一般的な解説だけでは、その研究で何に使ったのかが分かりません。 実験や調査の条件が書かれていなければ、読者は結果を評価できず、再現もできません。 目的、日時、対象者、回答者数と依頼した人数、手順、設定値を書いてください。

悪い例

図書室の利用者にアンケートを実施した。 5名から回答を得た。

良い例

蔵書検索の使いやすさを確認するため、2月3日から7日に図書委員12名へアンケートを依頼し、5名から回答を得た。 設問は付録 A に示す。

確かめる問い: この研究では、この技術を何のために使っていますか。 いつ、誰を対象に、どうやって調べましたか。

3.3 使った技術と外部の事実に出典を付ける

なぜ: 自分で確かめたことではない事実(技術の説明、統計、ほかの研究の結果)には、出典が要ります。 出典がないと、読者はそれが正しいのかを確かめられません。 規格書や公式の文書など、元の資料に当たってください。

悪い例

TCP は、データを確実に届けるためのプロトコルである。 近年、若者の読書離れが進んでいる。

良い例

TCP は、データの到達確認と再送によって信頼性のある通信を提供するプロトコルである[1]。 「大学生の読書に関する全国調査」[2]によると、1か月に1冊も本を読まない大学生は4割を超える。

確かめる問い: この説明の出どころはどこですか。 規格書や教科書と読み比べましたか。

3.4 図表は本文で導入し、説明する

なぜ: 「図に示す」とだけ書くと、読者は図から何を読み取ればよいのか分かりません。 何の実験かを説明してから結果を示し、図の読み方と図から何が言えるかを本文に書いてください。

悪い例

結果を図5.1に示す。 次に考察を述べる。 (この後の段落で)実験では2種類の方式を比較した。

良い例

2種類の方式で、応答時間を比較した。 応答時間の測定結果を図5.1に示す。 横軸は利用者数、縦軸は応答時間である。 利用者が50人を超えると応答時間が急に増えている。

確かめる問い: この図から何を読み取ってほしいのか、本文に書いてありますか。 どんな実験か分かる前に、結果を見せていませんか。

4. 話の流れを整える

4.1 理由と結論の間を省かない

なぜ: 書き手の頭の中ではつながっていても、途中の段階が書かれていなければ、読者には飛躍に見えます。 「A。このため B。」と書いたら、A が本当に B の理由になっているかを確かめてください。

悪い例

返却を忘れる利用者が多い。 そのため、書架を増やす必要がある。

良い例

返却を忘れる利用者が多い。 このため、貸出中のまま戻らない本が増え、借りたい本が書架にないことが多い。 書架を増やしても、この状況は変わらない。 必要なのは、返却を促す仕組みである。

確かめる問い: なぜそう言えるのか、と聞かれたら答えられますか。 「ため」の前と後は本当につながっていますか。 ほかの方法はありませんか。

4.2 段落は話のまとまりで分ける

なぜ: 段落は、ひとまとまりの話を入れるものです。 1文ずつ段落を分けると、話のまとまりが読者に見えません。 逆に、1つの段落に別の話が入っていると、読者は話が切り替わったことに気付けません。 前の段落の続きの話なら同じ段落にまとめ、話が変わるところで段落を分けてください。 「しかし」「そこで」から問題の提示や自分の研究の話に移るところは、段落の変わり目になることが多いです。

悪い例

本機能では貸出履歴を一覧で表示する。

一覧は新しい順に並ぶ。

一覧の行を押すと詳細を表示する。

本システムは蔵書を検索できる。 検索結果は書名順に並ぶ。 しかし、利用者からは予約状況が分からないという意見があった。 そこで、予約状況を表示する機能を追加する。

良い例

本機能では貸出履歴を一覧で表示する。 一覧は新しい順に並び、行を押すと詳細を表示する。

本システムは蔵書を検索できる。 検索結果は書名順に並ぶ。

しかし、利用者からは予約状況が分からないという意見があった。 そこで、予約状況を表示する機能を追加する。

確かめる問い: ここで段落を分けた理由は何ですか。 前の文の続きになっていませんか。 1つの段落に、別の話が入っていませんか。

4.3 同じことを繰り返さない

なぜ: 同じ内容を何度も書くと、論文が長くなるだけで、読者は何が新しい情報なのか探すことになります。 本筋につながらない節も、読者の時間を使わせるだけです。

悪い例

検索機能は語句で検索する機能である。 この機能により語句で検索できる。

良い例

検索機能は、入力した語句を含む蔵書を探す。

確かめる問い: 前の節と同じことを書いていませんか。 この節は、この先の話に必要ですか。

4.4 本文の中で記述を食い違わせない

なぜ: 同じことについて別の箇所に違う数値や説明があると、読者はどちらを信じればよいのか分かりません。 書き直した後に、古い説明が残っていることもよくあります。 本文と図表、本文とコードの食い違いも同じです。 数値、設定値、画面の要素の名前は、書いてあるすべての箇所を見比べてください。

悪い例

(2章で)貸出期間は2週間である。 (4章で)貸出期間は10日である。

良い例

(2章で)貸出期間は2週間である。 (4章で)試験運用では、返却を早めるため、貸出期間を10日に変更した。

確かめる問い: 前の章で書いたことと矛盾していませんか。 本文で説明したボタンは、図にありますか。 直した箇所の古い説明が、ほかに残っていませんか。

5. 文を整える

5.1 誰の動作かを明らかにする

なぜ: 主語がない、または主語と動作が合っていないと、利用者、管理者、システムのどれが動いているのか分かりません。 「〜される」のような受け身が混ざると、動作する者はさらに見えにくくなります。 理由がなければ、動作する者を主語にして「〜する」の形で書いてください。

悪い例

通知機能は、利用者の予約状況を確認して判断した。 停留所を選択すると、通知時刻が設定される。

良い例

本システムは利用者の予約状況を確認し、通知の要否を判定する。 利用者が停留所を選択すると、本システムが通知時刻を設定する。

確かめる問い: この「確認する」のは誰ですか。 画面や機能が、人の動作をしていませんか。

5.2 時制を章の役割に合わせる

なぜ: 設計や実装の章で「〜した」と書くと、今のシステムの説明なのか、過去にしたことの報告なのかが分かりません。 システムの設計や動作は、今そうなっていることとして「〜する」で書いてください。 過去形は、まとめの章で研究を振り返るときと、実験や調査で実際に起きたことを述べるときに使います。 「〜なってきている」のように変化を表す形は、変化を述べたいときだけ使います。 同じ節の中では、時制をそろえてください。

悪い例

(設計の章で)本システムは、入力された語句で蔵書を検索し、結果を一覧で表示した。 (評価の章で)検索時間は、従来より短くなってきている。 (まとめの章で)本研究では、蔵書検索の時間を短くする。

良い例

(設計の章で)本システムは、入力された語句で蔵書を検索し、結果を一覧で表示する。 (評価の章で)検索時間は、従来より短い。 (まとめの章で)本研究では、蔵書検索の時間を短くした。

確かめる問い: この文は、どの章の文ですか。 その章で過去形を使ってよいですか。 「なってきている」と書いて、何かが変わった話をしたいのですか。

5.3 文として成り立つか確かめる

なぜ: 主語と述語、目的語と動詞の組み合わせがおかしいと、読者は何を言いたいのかを推測するしかありません。 述語が抜けた文や、途中で形が変わった文も同じです。 主語と述語だけを抜き出して読むと、気付きやすくなります。

悪い例

プリンタが画面に検索結果を表示する。 処理時間が少ない。 一覧を自動化させる。 検索結果の一覧を確認の実施が可能を実現した。

良い例

アプリケーションが画面に検索結果を表示する。 処理時間が短い。 一覧の作成を自動化する。 利用者は検索結果を一覧で確認できる。

確かめる問い: 主語と述語だけを読んで、意味が通りますか。 何が何をするのか、声に出して説明できますか。

5.4 助詞と限定の語を選ぶ

なぜ: 助詞を取り違えると、文が不自然になります。 また、「は」「主要な」「など」は、文脈によっては、ほかにも何かあるように読者に思わせます。

悪い例

利用者は検索画面をキーワードに入力する。 予約システムの主要な機能は以下の2つである。(機能は2つしかない)

良い例

利用者は検索画面にキーワードを入力する。 予約システムの機能は以下の2つである。

確かめる問い: 声に出して読むと自然ですか。 「は」や「主要な」で、ありもしない対比を読者に想像させていませんか。

5.5 読点は意味の切れ目に打つ

なぜ: 読点が多すぎると文が細切れになり、少なすぎたり位置がずれていたりすると、係り先を読み違えます。 読点は、意味の切れ目に打ってください。 語を並べる読点と文の切れ目の読点が1文に混ざるときは、並べる側を「・」か「と」にします。

悪い例

本研究では、貸出履歴や、返却日時を、一覧で表示する。

学生を対象とした図書の検索機能と、著者名、書名、出版年、分類で検索結果を絞り込む機能がある。

良い例

本研究では貸出履歴や返却日時を一覧で表示する。

学生を対象とした、図書の検索機能と、著者名・書名・出版年・分類で検索結果を絞り込む機能がある。

確かめる問い: この読点を外すと、意味が変わりますか。 読点がないと、別の語に係って読めませんか。

5.6 「が」で文をつながない

なぜ: 「が」で文をつなぐと、文が長くなり、前と後ろの関係もぼやけます。 「〜したが、次に〜」のように、逆接でないのに「が」で続けるのは誤りです。 逆接の「が」は誤りではありません。 それでも文が長くなるので、文を分けて「しかし」などの接続詞でつないでください。

悪い例

本研究では蔵書検索アプリを開発したが、その画面構成を図3.1に示す。

本システムは複数の端末に対応しており、利用者は自宅からも操作できるが、管理画面は学内からのみ利用できる。

良い例

本研究では蔵書検索アプリを開発した。 その画面構成を図3.1に示す。

本システムは複数の端末に対応している。 利用者は自宅からも操作できる。 しかし、管理画面は学内からのみ利用できる。

確かめる問い: この「が」は逆接ですか。 「しかし」に置き換えて意味が通りますか。 文を分けると読みやすくなりませんか。

5.7 決まり文句で文を水増ししない

なぜ: 「〜を行う」「〜することができる」のような言い回しは、文を長くするだけで、中身を増やしません。 どの文も同じ動詞になり、単調にもなります。 全部をなくす必要はありません。 短く言えるなら、短くしてください。

悪い例

本研究では利用者アンケートの分析を行える仕組みの開発を行った。 本システムでは蔵書の検索を行うことができる。

良い例

本研究では利用者アンケートを分析できる仕組みを開発した。 本システムでは蔵書を検索できる。

確かめる問い: 「〜できる」「〜する」と短く言えませんか。 同じ言い回しが、ほかの文にもありませんか。

5.8 同じ語や要らない語を削る

なぜ: 1文の中や隣り合う文で同じ語が重なると、くどく読みにくくなります。 消しても意味が変わらない語(「実際に」「について」など)も、同じように文を重くします。 「本研究では」「また」のような前置きや接続語を、文ごとに付けるのも同じです。 どれも削ってください。

悪い例

検索の実行は検索ボタンで実行する。 在庫の管理のための在庫データの更新は在庫管理者が行う。

本研究では検索機能を開発した。 また、本研究では一覧機能を開発した。

良い例

検索ボタンを押すと検索を開始する。 在庫データは管理者が更新する。

本研究では検索機能と一覧機能を開発した。

確かめる問い: 声に出して読むと、くどくありませんか。 この章で「本研究では」は何回出てきますか。 この語を消すと、意味が変わりますか。

6. 語を選ぶ

6.1 同じものは同じ語で、違うものは違う語で呼ぶ

なぜ: 同じものを別の語で呼ぶと、読者は別のものだと受け取ります。 逆に、違うものを同じ語で呼ぶと、読者は同じものだと受け取ります。 機器とその上で動くアプリ、システムとその部品、元のシステムと今回作るものは、別の語で呼んでください。 自分で付けた名前は、論文全体を文字列で検索して、呼び方がそろっているかを確かめてください。

悪い例

本研究で開発する仕組みを「予約ナビ」と呼ぶ。 (後の章で)会員は通知を確認する。 登録者は通知を確認した後、本アプリを閉じる。

端末は利用者の位置を取得する。 端末は到着予測時刻を表示する。(1文目は機器、2文目はアプリを指す)

良い例

本研究で開発する仕組みを「予約ナビ」と呼ぶ。 (後の章で)会員は通知を確認した後、「予約ナビ」を閉じる。

アプリは端末から利用者の位置を取得する。 アプリは到着予測時刻を表示する。

確かめる問い: この2つの語は使い分けていますか。 同じものなら、そろえましょう。 同じ語で、別のものを指していませんか。

6.2 似た語の違いと関係を示す

なぜ: 似た語がいくつも出てくると、読者はそれらが同じものか違うものか判断できません。 並べた項目も、違いが書かれていなければ、なぜ分けたのか分かりません。 違うものなら何が違うのかを、関係があるならどういう関係なのかを書いてください。 システムとその部品、旧版と新版、手法とそれを使ったシステムの関係も同じです。

悪い例

運行情報を取得する。 次に、便情報を画面に表示する。

良い例

運行情報を取得する。 次に、運行情報から利用者が選んだ便の発着時刻を取り出し、便情報として画面に表示する。

確かめる問い: この2つの語は同じものですか。 違うなら、何が違いますか。 並べた項目は、それぞれ何が違いますか。

6.3 「何の」「何を」を省かない

なぜ: 「値」「結果」「割合」「データ」だけでは、何についてのものなのか分かりません。

悪い例

割合は30%であった。

良い例

全便のうち5分以上遅延した便の割合は30%であった。

確かめる問い: 何の割合ですか。 何の結果ですか。

6.4 語だけで対象が分かるようにする

なぜ: 「ボタン」「結果」「履歴」だけでは、どの画面の何を指すのか、読者は前後を読み直さないと分かりません。

悪い例

結果を保存する。 ボタンを押す。

良い例

検索結果を保存する。 テンプレート選択ボタンを押す。

確かめる問い: これは、どの画面の何のことですか。 一般的な話に読めませんか。

6.5 ぼかした語を具体的にする

なぜ: 「適切な」「様々な」「一定の」「不十分」「使いにくい」「など」のような語は、幅が広すぎて、読者は程度も中身も想像できません。 判断の条件は、実際の値で書いてください。

悪い例

暑いときは利用者に通知する。

適切な時刻に利用者へ通知する。

良い例

気温が30度以上のときは、利用者に水やりを促す通知を送る。

到着予測時刻の5分前に利用者へ通知する。

確かめる問い: 具体的には何が起こるのですか。 どれくらいですか。 「適切な」とは、具体的に何のことですか。 「など」には、ほかに何が入りますか。

6.6 話し言葉を使わない

なぜ: 「なので」「すごく」「一番」「だけ」「スマホ」のような話し言葉は、論文の文体に合いません。

悪い例

なので、一番人気がある本だけ表示するようにした。

良い例

したがって、貸出回数が最も多い書籍のみを表示する。

確かめる問い: 論文なら、この語をどう書きますか。

7. 提出前のチェックリスト

PR を送る前に、次のことを確かめてください。 どれも、エディタの検索、textlint の警告、文献欄の見直しで見つけられます。 textlint は日本語の文章の誤りを指摘する道具で、研究室の執筆環境に入っています。

どの形式でも

  • 誤字脱字がない。 助詞の重複(「をを」)、送り仮名の不揃い、製品名の綴りと大文字小文字を確かめてください。 差分だけでも読み返してください。
  • 全角と半角が正しい。 全角空白、全角の英数字、「,」と「、」の混在がないことを確かめてください。
  • ソースは1文ごとに改行している。 1行に何文も書くと、PR の差分でどの文を直したのかが見えにくくなります。
  • 文献を正しい場所で、正しい形で引用している。 引用の場所や形が正しくないと、何の根拠なのか、どの文献なのかが読者に分かりません。
    • 引用は、その文献で裏付ける語の直後か、裏付ける文の句点の前に置きます。
    • 先行研究を紹介するときは、著者に敬称(「氏」など)を付けず、論文を主語にします。 例: 「公開サービスへのトラフィックの解析」[3]では、…を分析している。
    • RFC や論文は、URL だけでなく、著者、タイトル、発行年などを書きます。 Web ページは、ページのタイトルと閲覧日を書きます。

LaTeX で書く場合

  • 番号を手で書いていない。 図表、章、節の番号は \label と \ref で書きます。 図表は組版で位置が変わるので、「以下の図」「上の表」のように位置で指さないでください。
    • 図表: 図\ref{fig:result}に示す
    • 節: \ref{sec:result}で述べる(「節」は付けない)
    • 章: 第\ref{chap:design}章
  • 英字の語と和文の間に空白がある。 空白がないと LaTeX がそこで行を折り返せず、長い語が右の余白にはみ出します。 数字と和文の間、句読点と括弧の隣、\ref と \cite の前には入れません。 例: 設定は timeout で指定する
  • 数値と単位の間に普通の空白を入れていない。 空白を入れずに 200Hz と書くか、細い空白 \, を使って 200\,Hz と書きます。 普通の空白だと、数値と単位が別の行に分かれることがあります。
  • \cite は句点の前に置いている。 例: 用いた\cite{sample}。
  • 特殊文字をエスケープしている。 _、%、$、~ は、そのままでは書けません(例: book\_id)。
  • レイアウトを手で強制していない。 本文に \\、\newpage を使わないでください。 図表の位置指定は [htbp] にし、[H] は使わないでください。
